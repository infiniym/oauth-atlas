# Haiku Live Guide evaluation — 31 October 2026

This is a small implementation evaluation, not a reliability benchmark or provider approval. Tests ran against the local app with public-source retrieval and real Anthropic requests. No paid provider account or customer credentials were used.

## Configuration

- Model: `claude-haiku-5-5`, confirmed available through the account's Models API, with structured-output and adaptive-thinking capabilities.
- Thinking: adaptive, medium effort. Thinking is enabled. The parser consumes final text separately from thinking blocks. Signed thinking blocks are retained only in memory if the same request needs a repair.
- Limits: 16,000 output tokens including thinking; 60 seconds shared by interpretation and at most one validation repair; 110 seconds for the complete website request.
- Key: ignored local Worker bindings file with owner-only permissions. No key was found in tracked source or the built output. Hosted secrets have not been configured or deployed by this change.

## Findings and changes

The initial text-only implementation explicitly disabled thinking. It produced relevant permissions and an actor question, but exact quotation copying failed repeatedly. It also asked redundant audience questions after an actor answer.

The model now selects numbered passages, and the server supplies the exact quotation. Local validation rejects unknown passages, unmatched scope identifiers, inconsistent published durations and unsupported guaranteed-turnaround language. One repair may fix rejected structure or citations; provider API errors are not retried as validation problems.

Confirmed choices now include both the original question and its answer. `customers` is explained as other customer organizations/workspaces, so the model should not ask that again using a distribution or installation label. Unknown provider policy remains a verification task rather than an intake preference.

An initial high-effort thinking run used 11,088 thinking tokens out of its 12,000-token output budget and stopped before producing a complete guide. Another reached the model deadline. Medium effort retained substantial thinking and completed the focused cases below. This does not establish that high effort is always worse; its former budget was insufficient for this workload.

## Judgment and remaining work

Haiku with thinking is viable for the focused Linear research-and-confirmation slice. Its actor-dependent guidance changed with the requirement and it produced useful setup checklists. This is not evidence that it can handle arbitrary apps reliably.

The sample also exposed planning and retrieval gaps. A Linear checklist placed successful token exchange before the customer-admin installation action; the prompt was tightened to require prerequisite order and distinguish implementation preparation from executed authorization. A follow-up real website run put callback preparation first, test-admin consent next, and successful token exchange afterward. Notion produced useful partial guidance but did not resolve the requested read-only grant, so it is not a complete success. The six-page retrieval limit may miss capability, distribution or approval sources. The system needs broader reviewed cases before claiming dependable unfamiliar-app coverage.

The validator does not generally prove that a source supports a claim or its applicability. Passage IDs remove invented quotation text; thinking can improve reasoning, but neither certifies truth. Exact provider setup and token exchange remain unexecuted. Browser automation was disabled in the local Work settings during the final follow-up, so the new model-enabled results were verified through the website API and database-backed reload, not a fresh browser interaction.
